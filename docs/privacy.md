# Data and privacy

This page describes the Python build, version 0.9.0. It is not a claim that hardware pause privacy, local-only network behavior, or the complete release security boundary has passed qualification. See the [Phase 7 checklist](phase-7-hardware-qualification.md).

## Local storage

Everything OpenMeet writes lives under one folder:

| Path within `%APPDATA%\OpenMeetPy\` | Contents |
| --- | --- |
| `meetings.db` | Meeting metadata, notes, transcripts, summaries, settings, full-text search copies, processing plans, request digests and counters, provisional text, live transcript lines, frozen saved-note snapshots, and calendar events read from your calendar feeds (never the feed addresses). |
| `meetings.db-wal`, `meetings.db-shm` | SQLite sidecar files that can exist while WAL mode is active. |
| `audio/<meeting ID>/` | Microphone and system-audio WAV files, timing indexes, and any repaired copies. |
| `stt/models/` | Downloaded Whisper `ggml` models and the Silero VAD file. |
| `stt/sherpa/<model>/` | Downloaded sherpa-onnx model folders and `silero_vad.onnx`. |
| `stt/sherpa/custom/<folder>/` | sherpa-onnx folders downloaded from Hugging Face, kept only when every file verified. |
| `stt/streaming/<model>/` | Pinned live transcript streaming models, downloaded only on a click and checked against a pinned size and SHA-256. |
| `stt/streaming/custom/<name>/` | Streaming model folders the user placed there. Read in place, never downloaded. |
| `local-ai/engine/<tag>-<backend>/` | The pinned llama.cpp build for this PC's graphics, including `llama-server.exe`. |
| `local-ai/models/` | GGUF models downloaded from the pinned Local AI catalog. |
| `local-ai/server.log` | llama-server's own output, appended across runs. |

`%APPDATA%` is `C:\Users\<you>\AppData\Roaming` unless the environment overrides it. The folder name `OpenMeetPy` is deliberately distinct from the earlier build's folder: this build never opens, migrates or writes that database. Copying data across is an explicit import (`OpenMeet.exe --import-from <old data folder>`).

Importing an earlier folder keeps everything on this device. The source folder is read only and never modified. The import refuses a destination that already holds meetings or audio, so it cannot merge or overwrite an existing library; an empty `meetings.db` there is moved to `pre-import-backup/<UTC timestamp>/` and kept (it is restored if the import fails). Stored credentials are blanked in the copied database (settings columns whose names contain key, token, secret or password), and the earlier build's speech models are not copied. A short report of counts is written to `import-report.txt` in the destination.

Markdown exports are separate files under the chosen destination's `Meetings` directory. The database, recordings, timing files, transcripts, models and exports are unencrypted. Device administrators, backups and sync software may access them. Choosing a cloud-synced export folder can move content off-device without an OpenMeet upload request.

Capture writes the selected microphone and system audio locally as two tracks. On Windows the system track records everything the chosen output plays, including OpenMeet's own playback, so it can contain unrelated application audio such as music or notifications. Sample and simulation creation is removed; historical fictional entries stay labeled and readable so edited notes are preserved. Automated tests use synthetic audio and fake devices.

## Network actions

| Explicit action | Destination | Sent or downloaded |
| --- | --- | --- |
| Download speech models | GitHub release hosts and Hugging Face, including their artifact delivery hosts. | Pinned model, VAD and live transcript streaming files, each checked against a pinned size and SHA-256. Meeting audio and notes are not uploaded. |
| Search Hugging Face / list files | Public Hugging Face API. | The search query or repository identifier; no meeting content or provider credentials. |
| Download a selected public model or folder | Hugging Face and approved HTTPS artifact hosts. | Revision-pinned file or a complete folder (every file checksummed) plus a local provenance manifest; no meeting uploads. |
| Test a connection | The base URL in the form plus `/models` (HTTPS, or plain HTTP only on loopback). | The key you typed, used for that one call and never stored, or the saved key and only for the URL it was saved with. Credentials only; no meeting content and no billable request. |
| Download the Local AI engine | github.com/ggml-org/llama.cpp releases. | A pinned llama.cpp build (CUDA with its CUDA runtime, Vulkan or CPU), checked against a pinned size and SHA-256. No meeting content. |
| Download a Local AI model | huggingface.co and its artifact hosts, from a pinned repository revision. | One GGUF file, checked against a pinned size and SHA-256. No meeting content or provider credentials. |
| Create summary | The saved AI-notes base plus `/chat/completions`. | Notes and transcript text with speaker names, model, template, saved instructions. No audio. |
| Enhance notes (and the automatic enhancement) | The saved AI-notes base plus `/chat/completions`; Local AI keeps it on this PC. | Your notes as typed, the final transcript with speaker names, model, template and saved instructions. If the transcript is too long for one request, the middle lines are left out and the result says so; no audio. |
| Ask this meeting | Same saved chat-completions route. | The question and that meeting's notes and transcript with speaker names; a follow-up also sends up to the latest 6 earlier questions and answers of its thread. If the whole meeting does not fit one request, only transcript excerpts chosen on this device by keyword match are sent, plus your notes (only their matching paragraphs if the notes are long) when they mention a keyword. No audio or other meetings. |
| Ask across meetings | Same saved chat-completions route. | The question plus notes, transcript text, speaker names, titles and start dates of only the 1 to 20 meetings your scope covers (all meetings, a folder, a tag or your picks), in one request; the answer is saved locally with its scope until you delete it or any of those meetings. If they do not fit one request, only locally chosen transcript excerpts are sent, plus each meeting's notes when they mention a keyword, and every selected meeting's title and start date still go with them. No audio, other meetings, or tag lists. |
| Rewrite with AI | Same saved chat-completions route. | Only the selected note text (up to 20,000 characters) and your rewrite request. No other notes, transcript, audio or meeting metadata. The result is shown, not stored, until you replace the selection with it. |
| First-run setup and Local AI speech-server detection | `http://127.0.0.1` ports 11434, 1234, 8888, 8000 and 8080 only. | `GET /v1/models` with no key and no meeting content, while setup or Settings is open. Setup offers only speech servers. The Local AI group names other chat servers already running as a hint and adds no connection by itself. A key typed for a detected server goes to the Credential Manager like any other connection. |
| Calendar feeds (Settings → Recording → Calendar; every 15 minutes, or Sync now) | The iCal address you added, over HTTPS only. Redirects are refused. | The request for the calendar file. Events (titles, times, locations, attendees from the file, and meeting links) are kept in the local database. Join links from events, including any passcode they contain, are stored locally with the event. The address is kept only in Windows Credential Manager. OpenMeet never writes to the calendar. |
| Meeting detection (opt-in) | Nothing leaves the device. | Every 3 seconds while on, reads which apps are using the microphone from the Windows microphone privacy store (app identifiers and usage times). Never audio. Ignored apps are stored locally. A detection only shows a prompt and flashes the taskbar entry; it never starts recording. |
| Automatic capture (second opt-in, off by default) | Nothing extra leaves the device; the recording then follows the same rules as a manual one. | When on, and only while meeting detection is on, a supported desktop call app (Teams, Zoom, Slack, Discord, Webex, Skype) seen using the microphone on two consecutive polls starts a normal recording with the devices saved in Settings. Browsers and other apps still only prompt. The recording bar shows it is automatic; Stop and Pause work as usual, and a manual stop or pause blocks an automatic restart for that call. A capture ends automatically only after the app has released the microphone for a grace period and you did not choose Keep recording. Call bookkeeping (app identifier, state, times, meeting link) is stored locally in `meetings.db`. If the live transcript or automatic processing points at a cloud connection, that applies to automatic recordings too. Timings are untested on real hardware. |
| Cloud transcription | The separately saved speech base plus `/audio/transcriptions`. | Finalized microphone and system audio as bounded WAV chunks, with model, language and vocabulary hint. |
| Live transcript on this PC | Nothing leaves the device. | The Transcription model, a streaming model, or a streaming folder on this PC. Audio and text stay local. |
| Live transcript with **Cloud connection** | The saved cloud speech base plus `/audio/transcriptions`. | Each finished utterance, up to 30 seconds, uploaded once. One recording sends at most 240 requests and 100 MiB, and no request is retried. |
| Automatic processing (Settings default) | The speech engine and optional AI notes connection set in Settings when the recording starts. | The final tracks after stop; saved notes and the final transcript only when an automatic summary is chosen. Only with **Enhance my notes after recording** turned on (off by default), the same notes and transcript also go in one more request after the summary. |
| Retry processing | The current speech and summary settings, for the existing stopped recording. | The remaining audio and text work, under new finite limits; earlier requests may already have been billed. |

There is no telemetry and no updater. Automatic processing is off (**Recording only**) by default; when you choose it in Settings it runs for every new recording. The **Live transcript** switch is on by default and runs on this PC with the Transcription model or a streaming model; **Same as Transcription** never uploads, and when Transcription is cloud it is unavailable. Live audio leaves the device only when **Cloud connection** is chosen as the live model. Development mode serves the UI from a Vite server on `127.0.0.1`. Dependency installation and builds contact package registries; those development tools are separate from anything the application sends.

Local scans read bounded directory entries and model headers; importing a candidate model reads and hashes the selected file. Scan results are not uploaded. Hugging Face search sends the query you typed, and listing files sends the selected repository ID. Downloads cover Whisper `ggml` files, complete sherpa-onnx folders, the two pinned live transcript streaming models, and the pinned Local AI engine and GGUF models; nothing else. Repository license metadata is kept in a local manifest. The Local AI group reads this PC's GPU name and dedicated memory through `nvidia-smi` and the display adapters Windows reports, system RAM through `GlobalMemoryStatusEx`, and `.gguf` files through the same read-only scan; none of that is uploaded. Opening Settings contacts no provider: it reads saved settings and local status, and the checks above stay on loopback. Opening Settings also starts the read-only scan of speech model folders, when the engine is on **On this PC**, and the Local AI hardware check, which reads this PC's GPU and RAM. Both stay on this device and upload nothing; a download, a **Test** or a summary still needs a click.

Model installation checks pinned sizes and SHA-256 hashes and happens only on an explicit action. Changing the selected model keeps existing downloads. Local transcription runs whisper.cpp or sherpa-onnx inside the app process with paths and settings passed locally; the sherpa runtime is part of the application, not a download. Downloaded sherpa-onnx folders are checked against the Hub's size and SHA-256 metadata at download time and then run from their own folder on this computer; nothing about them is sent back afterwards. Cancelling or failing a transcription keeps the previous transcript. Local transcription, cloud preparation and mapped timestamp seeking reject missing or damaged recording timing, and no transcript is published from a failed run; the original audio and index files are preserved.

## Credentials and cloud processing

There are no per-request confirmation cards or processing reviews (removed 2026-10-22). Each new recording attaches a plan built from the saved automatic-processing default; if the plan cannot be built, recording continues with processing off and a notice. Retry builds a new plan for an existing stopped recording and starts no capture.

The plan stored in SQLite holds non-secret destination and model metadata, scope, limits and revisions. It contains no API keys, credential account names, vocabulary prompt or meeting content. Separate workflow tables persist stage, attempt and run identity, sanitized failures, dispatch digests and byte counters, provisional text, and the saved-note snapshot acknowledged for a summary. Live transcript lines have their own table (`live_lines`, migration 032): unencrypted, marked provisional until a final transcript exists, and removed with the meeting. Those records are excluded from search, exports and summary input.

A plan allows up to 14,400 seconds of recording, 14,400 seconds of processing after stop, 256 MiB of uploaded audio, 1,000 requests and 800,000 UTF-8 text bytes. Text accounting uses the serialized request body in UTF-8 bytes, including generated combination requests. Cloud audio accounting reserves each request's frozen audio bytes and digest before sending. An uncertain request outcome does not refund budget. A speech or provider change during a run, the processing deadline, cancellation or exhaustion stops further dispatch and blocks stale publication. When the live model is **Cloud connection** and the final transcription also uses a cloud connection, the same interval can be uploaded twice and billed twice.

The recording worker copies only samples accepted for the saved track into a bounded queue per lane, and a full queue drops that block and marks the live transcript incomplete without affecting the saved recording. Paused audio is never written, so it never reaches the live queue. One worker thread decodes both lanes; a decoder failure stops live text with one sentence and never touches capture. Pause privacy on real hardware remains an open gate.

Final transcription replaces the stored transcript atomically. Automatic summaries use the final transcript and a saved-note revision acknowledged after stop; a failed note save blocks that summary and keeps your draft. Later note or transcript changes block publication of a stale summary. Closing the window saves notes and any open summary or transcript edit first, then stops capture, interrupts processing and quits. A save that cannot complete keeps the window open and lists it, and notes are never discarded. Restart never replays requests. An explicit retry creates a fresh run with finite limits and can continue after a successful final transcript, and it can repeat a request that was already billed remotely.

Settings takes a masked API key for each saved connection; the summary and speech assignments can share one connection. The key exists briefly in a password field in the page and in the request to the local server, and is then stored by the backend in the Windows Credential Manager through `keyring`, under service `OpenMeetPy` with a revision-specific account. The field clears after a save attempt, a connection change, a tab change and when the panel closes. No key is returned to the page or stored in React state, browser storage, SQLite, logs or exports. The page is JavaScript and cannot guarantee memory zeroization. Environment import and `.env` parsing are not used. Legacy provider keys stay dormant and are never forwarded to a new destination.

Changing a remote provider URL requires entering a key for that destination. Loopback HTTP allows an optional key; changing its destination discards the old credential reference. Editing a shared connection affects every assignment using it. Key replacement stores the new credential before publishing its reference in SQLite and then retires the previous one; a failed publication keeps the old working connection. A cleanup error reports partial success and reloads Settings, and a crash can leave an unused credential in the Credential Manager.

**Test** uses a key you typed for that one request and never stores it. A saved key is used only for the base URL it was saved with, so moving a connection to a new address needs the key again. **Local AI** has its own key: 32 random bytes generated once per install, kept in the Credential Manager under the **Local AI** connection's account, and passed to `llama-server` in the `LLAMA_API_KEY` environment variable rather than on the command line, where a process listing would show it. It is not written to SQLite, `server.log`, exports or the page.

When AI notes is assigned to **Local AI**, summaries, questions, rewrites and automatic summaries go to that server's `/v1/chat/completions` on `127.0.0.1` on this PC. Notes and transcript text do not leave the device on that path, no audio is sent, and provider terms, retention and billing do not apply.

Manual summaries, questions (per meeting or across meetings), rewrites and cloud transcription send only when you use them, to the connection assigned in Settings; Settings marks each connection **This device** or **Leaves this device**. Every provider in the connection list (OpenAI, Claude (Anthropic), Gemini (Google), Mistral, Groq, Grok (xAI), DeepSeek, OpenRouter) is a third party that receives meeting text (AI notes) or audio (cloud transcription) only when you assign it and run an action. The **Leaves this device** rule is unchanged and follows the destination. The provider list and its endpoints are covered by mocked HTTP tests only, not tested against the live services. Provider terms and billing apply after submission. Local Whisper remains the default and uploads nothing. OpenMeet cannot retract uploaded audio or control a provider's retention. Cancellation prevents later uploads and publication, but a request already in flight can finish remotely and be billed.

Long summaries split transcript segments into bounded requests, then combine the partial results with your notes; the largest plan is eight chunks plus one combination request. Input over the limit is refused rather than truncated, and more requests than the plan allows are refused. Cloud audio is prepared as frozen temporary PCM WAV chunks, and preparation fails if the source file changes meanwhile. Those scratch files are unencrypted and are removed when preparation or execution ends. There is no automatic capability-probing upload and no automatic billable retry.

Summaries are saved separately from your notes with provider, model and template metadata; older versions stay readable and export uses the latest. Tasks are stored locally, unencrypted, and are included in Markdown exports. Importing tasks from a summary sends nothing; editing a summary sends nothing and is stored locally as a new version. Transcript edits and earlier transcripts are also local and unencrypted, and corrected text is what later summaries, questions and exports use. When a question's content is too long for one request, OpenMeet searches the selected transcripts and notes on this device for the question's keywords (a lexical match, not a semantic one) and sends only the matching transcript lines with up to two neighbouring lines each side, plus the notes or their matching paragraphs, within the request budget. Editing an excerpted line while an answer is pending stops it from being saved. When nothing matches, nothing is sent and no provider is contacted: the app shows "No passages in the selected content matched your question. Nothing was sent." and stores no question turn. The model is told that only excerpts are included and to answer "Insufficient evidence in the provided excerpts" rather than guess. Content that fits in one request is sent in full. Questions and answers are saved in threads with the meeting, with provider and model, locally and unencrypted, and are not exported. A follow-up sends up to the latest 6 earlier question and answer turns of that thread, marked to the model as quoted earlier conversation rather than instructions; a turn that arrives while an answer is pending stops that answer from being saved, and a thread too long to send is refused rather than truncated. Failed or cancelled questions store nothing. Deleting a thread (after confirmation) or the meeting removes its saved questions and answers. Answers across meetings are saved the same way with the ids of the meetings sent, and deleting the answer or any one of those meetings deletes it. Recipes are stored locally as question text; choosing one sends nothing. Copy buttons put summary text on the system clipboard, where other software may read it.

## Local server boundary

The backend is a FastAPI application served by uvicorn bound to `127.0.0.1` on a free port chosen at launch, and the window is a WebView2 view of that page. `/api/invoke`, `/ws` and `/files` require a per-run token: 32 random bytes generated at launch (`secrets.token_urlsafe(32)`), injected into the served `index.html` as `window.__OPENMEET_TOKEN__` and sent back in the `X-OpenMeet-Token` header (or the `token` query parameter for `/ws` and `/files`). `/health` and the static page with its assets are served without a token, and the index page itself carries the token, so any process on this computer that can reach the loopback port can fetch that page, read the token and then call the API. The token is not a defense against other local processes running as the same user. `/api/invoke`, `/ws`, `/files` and `/` also check the `Host` header, so a page on another name that resolves to loopback is refused; `/health` and the mounted static files do not. `/files` serves only files inside the data folder's `audio/` directory and the chosen export folder, resolves the path first, and refuses database files outright. The data folder itself is never served; static files are the built UI only.

There is no CORS middleware and no packaged content-security policy, so the boundary is the loopback binding, the `Host` check and the token rather than a CSP header. The window is the only intended client. These controls still need an independent end-to-end boundary review; they are not a completed security audit.

The managed **Local AI** server is a second loopback listener, on `127.0.0.1` at port 39281 or a free port, and it answers only requests carrying its own key. Like the app's port, it is reachable by other processes running as the same user, and a process that can read the `llama-server` environment can read that key. It is never bound to another interface.

## Retention, deletion, and backups

There is no automatic retention cleanup. Audio, including partial files, stays until you delete it. **Recover audio** writes repaired copies beside the original partial WAVs; the originals remain, so recovery needs extra disk space. The Local AI engine and its downloaded models also stay until **Remove** deletes one model or the data folder is deleted.

**Delete audio** removes the tracked audio and timing files and any other regular files directly in that meeting's audio folder, including recovery copies. Notes, transcripts and summaries stay. **Delete meeting** also removes the meeting and its database rows, including search entries. The UI asks for the meeting title to confirm; the backend refuses to delete the active recording. There is no undo.

Deletion is not secure erasure. OS backups, sync copies and unreclaimed database or disk space may retain content. Exported snapshots are never deleted by these operations. Path handling is guarded, but the symlinked-folder case stays part of hardware qualification.

Before a backup, wait for **Saved**, close the app normally, and copy the whole data folder plus your exports separately. Do not copy or replace only a live `meetings.db` and assume it holds every committed WAL write, and do not reset or delete the database as troubleshooting.

## Saving and recording limits

Autosave waits 400 ms and serializes writes. Closing the window saves notes and any open summary or transcript edit, then quits with no prompt. A save that fails shows **Not saved yet** with **Try again**, **Keep working** and, for a summary or transcript edit only, **Quit anyway**. Notes are never discarded, so a failed note save has no **Quit anyway**. A forced termination or power loss can lose unsaved text. A stop request shuts capture down without waiting for a note save; a failed draft stays on screen.

Real recording needs working device access, and telling participants is your responsibility. The code has pause controls and tests that reject queued samples from an earlier pause generation. Excluding paused audio on real hardware, failure behavior, timing accuracy and local-only egress still need qualification; use authorized synthetic content for those checks. Recording-consent law is your responsibility; the app enforces no consent checkbox.
